# 为什么 IP 访问规则使用独立缓存

本文只解释缓存与一致性设计；请求链、限流、自动封禁、本地端口测试和部署排错参见[《IP 访问控制与自动安全防护》](ip-security-protection.md)。

## 结论

IP 访问规则使用独立 `IP_ACCESS_RULES` 缓存，不是因为它是外部服务或特殊运行组件，而是因为它有独立的数据表、写事务和高频请求读取路径。它仍由统一的 `RuntimeCacheRegistry` 管理：

```text
RuntimeCacheRegistry
├── RUNTIME_SETTINGS   system_settings 表中的运行时设置
└── IP_ACCESS_RULES    ip_access_rules 表中的结构化规则
```

两者共享相同的 revision 对账、手动刷新、状态报告和失败隔离机制，但分别加载，避免修改一条 IP 规则时无意义地重载全部运行时设置。

## IP 策略只有一个有效来源

请求过滤器只读取 `IpAccessRuleService` 的结构化快照，不再组合 `security.ip.allow-list` 与 `security.ip.deny-list` 字符串。升级启动时，迁移器会：

1. 读取旧字符串中的 IPv4、IPv6 或 CIDR；
2. 规范化并去重后写入 `ip_access_rules`，来源标记为 `MIGRATED`；
3. 删除旧运行时设置键；
4. 递增两个缓存 revision，并在事务提交后刷新本机快照。

这样后台“IP 访问规则”页面就是唯一事实来源，不会再出现配置页有黑名单、规则页却为空的冲突。

每条规则包含类型、网段、来源、作用域、有效期、原因、违规次数、首次/最近触发时间、封禁时间和撤销时间。来源包括：

- `MANUAL`：管理员创建；
- `MIGRATED`：由旧字符串名单迁移；
- `AUTO_RATE_LIMIT`：连续触发限流后自动生成；
- `AUTO_LOGIN_ABUSE`：为后续按来源 IP 的登录滥用保护预留。

规则状态由时间与撤销标记实时计算为 `ACTIVE`、`EXPIRED` 或 `REVOKED`。删除接口实际执行撤销，历史记录不会物理删除。

## 判断优先级

同一客户端可能同时命中多类规则，固定优先级为：

```text
人工或迁移 DENY
  > 显式 ALLOW
  > 自动 DENY
  > ALLOW 模式的默认拒绝
  > 默认允许
```

因此管理员可以用显式 allow 保护可信运维地址不受自动封禁影响，但显式 allow 不能绕过管理员主动创建或从旧配置迁移的 deny。只要存在任一有效 allow 规则，系统进入白名单模式，未命中的来源默认拒绝。

运行时配置、缓存和 IP 规则管理接口绕过 IP 规则过滤，以保留恢复入口；它们仍要求 RBAC 权限，并使用独立的控制面限流桶。

## 为什么不能每次请求查询数据库

IP 判断位于 `/api/**` 过滤链上。每次请求查表会额外占用数据库连接、把数据库延迟传导到全部接口，并在数据库抖动时放大故障。因此请求只读取不可变内存快照；数据库只在启动、规则变更、revision 变化或管理员手动刷新时读取。

规则到期不需要刷新。快照保留 `expiresAt` 与 `revokedAt`，每次判断都使用当前时间计算是否有效；revision 刷新负责发现规则集合变化，当前时间负责处理自然过期。

## 写入、发布和多实例对账

人工创建、撤销或自动封禁时执行：

```text
写入 ip_access_rules
  → 同一事务递增 IP_ACCESS_RULES revision
  → 数据库提交成功
  → 原子发布本机新快照
```

事务回滚时不会发布快照，因此不会出现数据库写入失败、当前进程却已使用新规则的“幽灵状态”。其它实例定期只查询 `runtime_cache_revisions` 中该 Provider 的一行 revision；只有 revision 变化时才全量加载规则。管理员也可调用：

- `POST /api/v1/system/runtime-caches/IP_ACCESS_RULES/refresh`
- `POST /api/v1/system/runtime-caches/refresh`

单个 Provider 加载失败时保留旧快照并记录脱敏错误，不会清空规则，也不会阻止其它 Provider 完成刷新。

## 自动临时封禁如何工作

全局或端点限流返回 429 时，`IpAbuseTracker` 按客户端 IP 记录一次拒绝。同一 IP 在配置观察窗口内达到阈值后，系统创建有期限的 `AUTO_RATE_LIMIT` deny；后台规则页会直接显示该 IP、触发策略、违规次数、封禁时间和失效时间。重复触发会更新已有有效自动规则，而不是不断创建重复记录。控制面 429 不进入该状态机。

限流和触发计数使用最多 100,000 个状态的 Caffeine 单机缓存，并按时间淘汰；真正的封禁规则持久化在数据库中。回环、任意本地和组播地址不会自动封禁，避免本地开发或同机代理自锁。自动封禁写库失败时只记录错误，原请求仍按 429 返回。

这仍不是分布式限流：多实例会分别计数，只共享已经落库的封禁结果。需要严格的集群级阈值时，应将计数器替换为 Redis 等共享存储，`IP_ACCESS_RULES` 的持久化与缓存机制可保持不变。

## 何时应该成为独立 Provider

一份数据如果拥有独立数据源、独立写事务、位于高频请求路径、需要独立刷新/报错或需要多实例对账，就适合成为统一缓存注册表中的独立 Provider。IP 规则同时满足这些条件，因此独立缓存是统一框架下的标准实现，不是一个额外服务依赖。
