# 为什么 IP 访问规则使用独立缓存

## 结论

持久化 IP 访问规则使用独立缓存，不是因为它在产品上比其它配置更重要，而是因为它拥有独立的数据表、数据模型、修改入口和请求期读取方式。它与运行时设置属于两个不同的一致性边界。

当前统一缓存注册表首批包含：

```text
RuntimeCacheRegistry
├── RUNTIME_SETTINGS   system_settings 表中的运行时设置
└── IP_ACCESS_RULES    ip_access_rules 表中的持久化 IP 规则
```

`IP_ACCESS_RULES` 只是普通的 `RuntimeCacheProvider`。未来其它需要“数据库持久化、请求期内存读取、跨实例自动对账”的数据，也可以按相同方式接入。

## 两种 IP 策略不是同一份数据

系统目前存在两种 IP 策略来源。

### 运行时字符串策略

- `security.ip.allow-list`
- `security.ip.deny-list`

它们是 `system_settings` 表中的普通运行时设置，适合保存简单、全局的逗号分隔 IP/CIDR 列表。它们跟随其它运行时设置一起进入 `RUNTIME_SETTINGS` 快照。

### 持久化 IP 规则

持久化规则保存在独立的 `ip_access_rules` 表中，每条规则具有独立结构：

- 规则类型：`ALLOW` 或 `DENY`；
- IPv4、IPv6 或 CIDR 网段；
- 作用域；
- 可选失效时间；
- 管理备注；
- 独立 ID 和 CRUD 生命周期。

这种数据不是一个字符串配置值，不能自然地塞进某个运行时设置键。它由独立管理接口创建和删除，因此也需要独立的缓存发布与失效协议。

## 为什么不能在每次请求时查询数据库

IP 判断位于 API 请求过滤链上，几乎每个业务请求都会执行。如果每次请求都查询 `ip_access_rules`：

- 每个 API 请求都会额外占用一次数据库连接和查询；
- 数据库延迟会直接进入所有接口的响应时间；
- 数据库短暂抖动可能放大成整个 API 的可用性问题；
- 高并发下规则读取会与正常业务查询争抢连接池。

因此，请求路径只读取 `IpAccessRuleService` 中的不可变内存快照。数据库只在启动、规则变更、revision 对账或管理员手动刷新时读取。

## 为什么不并入 `RUNTIME_SETTINGS` 缓存

把两份数据强行合并，技术上可以实现，但会产生不必要的耦合：

1. 修改一条 IP 规则会迫使所有运行时设置重新加载。
2. 修改 CORS、限流或 GC 周期时，也会无意义地重新查询全部 IP 规则。
3. 一个缓存的加载失败会影响另一类本来正常的数据。
4. 管理页面无法准确展示各自的 revision、条目数和加载错误。
5. 后续增加更多独立配置表时，单个“大而全快照”会持续膨胀。

独立缓存使刷新范围与数据库事务边界保持一致：`system_settings` 变化只更新 `RUNTIME_SETTINGS`，`ip_access_rules` 变化只更新 `IP_ACCESS_RULES`。

## 写入和刷新流程

创建或删除持久化 IP 规则时，流程如下：

```text
管理请求
  → 写入 ip_access_rules
  → 在同一事务递增 IP_ACCESS_RULES revision
  → 提交数据库事务
  → 提交成功后重新加载并发布本机快照
```

关键约束是“提交后发布”：

- 事务成功，本机立即使用新规则；
- 事务回滚，旧快照保持不变；
- 不会出现数据库没有成功写入、但当前进程已经使用新规则的幽灵状态。

多实例部署时，其它实例不会依赖进程内事件。自动刷新任务定期读取 `runtime_cache_revisions` 中 `IP_ACCESS_RULES` 的单行 revision：

```text
数据库 revision == 本机 snapshot revision
  → 不加载规则表

数据库 revision != 本机 snapshot revision
  → 全量加载规则并原子替换本机快照
```

这种方式把日常自动检查控制为一次很小的 revision 查询，只有真正发生变化时才读取规则表。

## 手动重载的用途

管理员可以通过以下接口强制重载：

- `POST /api/v1/system/runtime-caches/IP_ACCESS_RULES/refresh`
- `POST /api/v1/system/runtime-caches/refresh`

手动重载适用于：

- 自动刷新被关闭；
- 需要立即确认数据库与本机快照一致；
- 排查某个实例的缓存状态；
- 数据通过应用之外的受控方式维护，revision 没有同步递增。

强制重载失败时，服务保留上一份可用快照，并在缓存状态中记录失败时间和脱敏错误消息，不会先清空规则再尝试加载。

## 规则过期是否需要刷新

不需要。

快照会保存规则的 `expiresAt`，每次进行 IP 判断时都使用当前时间检查规则是否仍然有效。因此规则到达失效时间后，即使没有执行缓存刷新，也会立即停止参与判断。

缓存刷新负责发现“规则集合发生变化”，而当前时间负责判断“快照中的规则现在是否有效”，两者职责不同。

## 与运行时配置的最终关系

请求过滤器会组合两份内存数据：

```text
RUNTIME_SETTINGS
  → security.ip.allow-list / deny-list

IP_ACCESS_RULES
  → 结构化、可过期的持久化规则

两者共同参与最终 ALLOW / DENY 判断
```

所以，独立缓存不代表独立执行安全策略。它只表示两种数据各自加载、各自刷新、各自记录 revision，最终仍在同一请求过滤链中合并判断。

## 设计原则

判断一份数据是否应该成为独立缓存 Provider，主要看以下条件：

- 是否拥有独立数据源或表；
- 是否拥有独立写事务；
- 是否在高频请求路径中读取；
- 是否应该独立刷新和报告错误；
- 是否需要多实例对账。

持久化 IP 规则同时满足这些条件，因此使用独立 `IP_ACCESS_RULES` 缓存。它不是硬编码的例外，而是统一缓存框架中的一个标准实例。
